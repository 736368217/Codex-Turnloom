# 手机端能力盘点与发展方向（2026-11-05）

> 面向「成熟的远程编码 / 会话客户端通常有什么，我们还缺什么，能不能支持」。
> 结论基于本项目真实 API、Android 壳与 PI-Desktop 宿主契约，不臆造竞品数据。
> 标记：**已有** = 现在就能用；**可做** = 本仓库内可实现；**需宿主** = PI-Desktop 得先提供 operation；**不建议** = 成本/收益不划算。

## 一、我们已经有的（别重复造）

| 能力 | 实现位置 |
|---|---|
| 多设备添加/切换、二维码、访问码 Keystore 加密 | Android 原生 + `/api/auth/session` |
| 会话列表：项目(=文件夹)分组、置顶、搜索、状态总览与筛选 | `threads.js` / `app.js` / `styles.app.css` |
| 消息流：Markdown、图片、工具/内部记录收起、压缩提示、连续发言人合并 | `app.js` / `markdown.js` |
| 状态：运行中 / 待处理 / 疑似停滞 / 已完成 / 未知，顶栏徽标 + 列表状态条 | 本轮新增 |
| 发消息、排队、插入打断、停止、附件（图片/文件）、重试 | `/api/send` `/api/queue/*` `/api/interrupt` |
| 模型选择（常用/全部/搜索）、思考强度、插件与技能引用 | `/api/health` `usedModelIds` |
| 目标（goal）查看/编辑/暂停、置顶、提醒通知、本地文件下载 | `/api/threads/:id/goal`、Android 通知 |
| 分支（从某条消息）、压缩、审批响应 | `/api/threads/:id/branch` `compact` `/api/approval` |
| 长按复制/选择文字/创建分支、应用内确认弹层、软键盘自适应 | 本轮 + 上轮 |
| 开机静默自启、健康守护与自愈、公网隧道 | `link-watchdog.mjs`、计划任务 |

## 二、成熟客户端常见、我们**还缺**的能力

### A. 可在本仓库内直接做（不需宿主改动）

| 功能 | 价值 | 现状 | 建议优先级 |
|---|---|---|---|
| **全文搜索消息内容** | 目前只能搜会话标题/预览；找不到"上次那句命令在哪" | 缺 | ★★★ 高。服务端已有 rollout/messages 读取，加 `/api/search?q=` 扫描最近 N 条即可，手机端做结果列表跳消息 |
| **会话重命名** | 列表里一堆「New task」「(branch)」，用户认不出 | 缺 UI；宿主有 `session/rename` | ★★★ 高。桥已能调宿主 operation，补一个菜单动作 |
| **归档/隐藏会话** | 临时对话不该只靠软删除 DB 行 | 仅 `prune-session-artifacts.mjs` 离线脚本 | ★★☆ 中。做 UI「归档」，走宿主的 deleted/archived 语义 |
| **草稿持久化** | 输入一半切会话/切设备，字就没了 | 缺 | ★★★ 高。localStorage 按 threadId 存草稿，回来自动恢复 |
| **消息内代码一键复制 / 代码块折叠** | 长代码块刷屏 | 只有整条复制 | ★★☆ 中。渲染 markdown 时给 `pre` 加复制按钮与折叠 |
| **语音输入 / 粘贴图片** | 手机打字成本高 | 缺 | ★★☆ 中。用系统 IME 语音（无需权限）；粘贴监听 clipboard image |
| **通知直达会话** | 完成提醒点开只到首页 | 提醒已有，但深链未接 | ★★☆ 中。PendingIntent 带 threadId → `targetUrl(device, threadId)` |
| **多会话并行状态推送** | 现在靠 3 秒轮询 | 已有轮询 | ★★☆ 中。改为 SSE/长轮询，省电并让徽标更即时 |
| **主题/字号设置** | 用户曾明确说"不需要深色模式"，但字号可调仍有价值 | 缺 | ★☆☆ 低。仅字号，别再做主题 |
| **导出对话 / 分享** | 把一段排查结果发到别处 | 缺 | ★★☆ 中。纯文本/Markdown 导出走系统分享 Intent |
| **空状态与错误的可操作指引** | 已有 retries，但离线/无会话仍偏空 | 部分 | ★★☆ 中 |

### B. 需要 PI-Desktop 宿主先支持（不是我们单方面能补）

| 功能 | 为什么卡在宿主 |
|---|---|
| **多会话并发控制、真正的 agent 暂停/恢复** | 宿主目前只有 `agent/abort`/`agent/stop`，没有 pause/resume 的 operation；桥返回 "unsupported method" 就是这类 |
| **精细化权限策略（按命令/目录记住允许）** | `approval/respond` 存在，但持久策略在宿主侧 |
| **工作区 / worktree 切换与差异预览** | 宿主有 `session/moveProject`，无 diff/文件树读取契约 |
| **多账号 / 用量与配额可视化** | `/api/account` 只暴露基础信息；配额在宿主 provider 层 |
| **会话级成本/token 统计** | 门面库有 `usage_json`，但没有按会话聚合的宿主 API |

> 这类不要伪装成"已支持"。真要做，先在桥里加 `thread/xxx` handler + 宿主 operation 探测，能力面板如实显示"当前宿主不支持"。

### C. 不建议在本项目做

- **端到端加密 / 多用户账号体系**：当前是「自己电脑 → 自己手机」的私有链路，已有 HTTPS + 访问码；引入账号体系会破坏离线可用与部署简单性。
- **完整原生重写（RN/Flutter）以追求"更不像网页"**：本轮已把长按选词、系统弹窗、原生 select 这些**真正暴露 WebView 的交互**接管掉；再往下是投入产出比问题，除非用户明确立项，否则按页面渐进迁移，不整体推翻。
- **内置浏览器/网页预览**：宿主会话里的链接交给系统浏览器即可，别在 App 里再套一层 WebView。

## 三、建议的发展顺序

1. **先补"找得到、认得出、不丢字"**：全文消息搜索 → 会话重命名 → 草稿持久化 → 归档 UI。这四个都是高频痛点，且完全不依赖宿主。
2. **再补手机原生体验**：语音/粘贴图片、通知深链、代码块复制、导出分享。
3. **然后做协议层升级**：状态改推送（SSE）、能力探测面板（把宿主不支持的能力明确标灰）。
4. **最后才评估原生重写**：若到时候用户仍觉得"像网页"，按页面逐个用原生组件替换（建议从会话列表 + 消息流开始），服务端协议不动，双端并行验证。

## 四、本轮交付与验收口径

- 键盘遮挡：`visualViewport` + `--app-visible-height` + `html.keyboard-open` 收紧 composer；320×300 下 composer 底部 = 300 = 可视区底部，发送键可见，消息区仍可滚。
- 质量检定：125/125 ×3 次稳定、语法、CSS 括号、Android 单测、桥四套全绿。
- 易用性检定：主聊天/抽屉/模型常用/模型全部/键盘态逐屏，0 JS 错误、0 横向溢出、0 个 <44px 控件、对比度 5.0–17.9。
