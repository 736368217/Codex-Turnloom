## 过程中的两个坑

1. **`736.de5.net` 上有 Worker catch-all 路由 `*/* -> tarot-app`**，任何子域名的 `/api/*` 都会被
   该 Worker 截走并返回它自己的 `API_NOT_FOUND`。因此入口最终落在没有 catch-all 的 `z736.cc.cd`。
2. **Cloudflare Tunnel 从这台大陆服务器出来的边缘是 LAX**（隧道 4 条连接分别落在 lax01/lax07/lax08），
   每请求额外 0.5–0.9 s。功能可用，但对话类交互偏慢，故保留为备用而非默认。

## 三端拆分与桌面端「服务端」选择（同日第二轮）

用户明确要求把链路拆成 **手机端 / 桌面端 / 服务端** 三层：服务端是一台可替换的中转入口，
桌面端负责「选哪个服务端 → 连接」，以后换服务器只改桌面端，不动手机。

### 配置层

- `config.json` 新增 `servers[]` 与 `activeServerId`；每个条目 = `{id, name, publicUrl, tunnel{host,user,remotePort,keyPath,knownHostsPath}}`。
- `publicUrl` / `tunnel` 由**活动条目派生**（`applyActiveServer`），配对二维码、隧道、守护脚本继续只读这两个旧字段，无需改调用方。
- 旧配置首次加载自动迁移成一个 `srv-local` 条目，行为不变；`network.mode = direct` 时不会被条目重新填回公网地址。
- 表单编辑 `publicUrl`/`tunnel` 时先用 `syncActiveServer` 回填活动条目，再统一派生，避免「改了地址但条目没改」。
- 新 IPC：`servers:list` / `servers:save`（`activate:false` 只保存不切换）/ `servers:activate` / `servers:remove`；与 `config:save` 共用 `applyConfigPatch`，走同一条校验→落盘→`runtime.applyConfig` 路径。

### 桌面端界面

设置 →「访问方式与公网转发」顶部新增：服务端下拉 + **连接** + 新增服务端 / 删除当前 + 服务端名称。
选另一台服务端再点「连接」，隧道与配对二维码一起切过去；手机端地址不变（域名不变时无需重新配对）。

### 控制台显示过期地址的根因

旧地址 `https://121.40.69.97:18787` 一直显示在配对面板上，不是配置没改（`config.json` 早已是新值），
而是**运行中的控制台只在启动时读一次配置**，且没有文件监听。本轮加了 `watchConfigFile()`：
`config.json` 变化后 400ms 内重载并 `sendState()`，界面不再需要重启控制台才能看到新地址。

### 手机端「停止连接」

连接旧地址或不可达地址时原先只能等超时。现在连接过程中除主按钮外多一个 **停止连接**：

- `stopConnecting()`：`transitionSeq += 1` 作废本次尝试 + `cancelAllNativeRequests()` 取消在途请求；
- 已配对的电脑回到 `error`（可直接重试或改地址），从未连过则回 `unpaired`；
- 连接页只在 `working`（checking / connecting / reconnecting）时渲染该按钮。

## 扫码主路径阻塞修复（同日第三轮，用户实测报障）

现象：手机扫码后提示「多服务模式下机器访问码不能同时作为服务访问码」，连接完全无法完成。

### 根因

`machine.json` 的 `legacyMachineTokens` 里残留着旧机器码 `684271`，而 `684271` 同时是
`codex` 服务的访问码。网关把 `legacyMachineTokens` 也算作合法的发现凭据，于是：

1. 手机若用这个旧码配对，网关接受发现请求；
2. 手机拿到 harness 列表后发现「机器码 == 某个服务码」，客户端一致性校验直接拒绝。

桌面端保存配置时只校验 `machineToken != 各 harness token`，**没校验 `legacyMachineTokens`**，
所以这份冲突配置一路被放行到手机上才爆。这是主路径上的死锁，不是边缘场景。

### 修复

| 层 | 改动 |
|---|---|
| `desktop/service/machine-gateway.cjs` | `legacyMachineTokens` 也纳入校验：多 harness 模式下不得等于任何 harness token，保存即报错 |
| `shared/machine-pairing.cjs` | 只有**多服务**才判定「机器码 == 服务码」；单服务同码是文档允许的兼容部署，放行。错误文案点名冲突服务 |
| `app/src/lib/machinePairing.ts` | 同上规则；并把 `machine-token-reuse` 等校验类错误的文案提到「连不上」之前，避免被传输文案盖掉 |
| 运行配置 | 清空 `machine.json` 的 `legacyMachineTokens`（改前备份 `machine.json.bak-legacy-*`） |
