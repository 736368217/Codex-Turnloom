## 主问题：会话永久停在「加载中」

**根因（已复现）**：`codexHomeVersion` 在会话运行期间每次写入都会自增。`applyHomeContext()` 原本把「版本号变化」当成「更换了 Codex 主目录」，于是每 3 秒一次的列表同步都会清空正在阅读的会话（`lastMessagesData = null` + 消息区替换为加载态）。而该同步只调用 `loadThreads()`、不调用 `loadMessages()`，所以列表再也没有恢复。

实测证据：修复前，页面加载 2.4 秒内消息正常（41 条），约 3.4 秒时被替换成加载态并持续为 0 条、不再有网络请求；`codexHomeVersion` 连续三次采样为 150 → 151 → 151。

**修复**：
1. `applyHomeContext()` 只在**主目录路径真正变化**时重置视图；版本号照常更新（消息缓存键本就包含版本号，缓存仍会失效）。
2. 周期同步在发现「已选会话但消息被清空」时自动补载。
3. `/api/health`（15s）与 `/api/threads`（20s）补上超时——此前只有消息接口有上限，连接一卡首屏就无声地永久停在加载态。

**验证**：修复后连续 18 秒、13 次采样，消息稳定在 41 条，`loading` 始终为 false，无一次清空。

## 同时修复：样式表拿不到缓存失效指纹

服务端 `withAssetVersions()` 用 `(?:href|src)="(\/[^"?#]+\.(?:css|js))"` 收集本地资源，`[^"?#]+` 明确排除了 `?`。我在 `index.html` 的 v3 link 上写死了 `?v=1.17.10`，于是该引用完全匹配不上、被永久钉在同一个 URL —— 之后每次改样式都可能被浏览器/WebView 缓存挡住（这正是"改了却没生效"的隐患）。

现已改回裸引用，实测服务端下发 `/styles.v3.css?v=mvtbpcne-v9e`；并新增测试要求 `index.html` 中的本地 css/js 引用一律不带查询串。
