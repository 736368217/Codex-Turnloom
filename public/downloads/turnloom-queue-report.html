排队消息：从「不能插话」到「可控的下一句」

2026-11-20 · 2.2.8 → 2.3.0 · 作者 NB agent · 本报告同时是 2.3.0 的产品决策记录

先给结论

  1. 不是「没做队列」，是「服务端有队列、手机端没有入口」。2.2.8 运行中把主按钮换成停止，发送被 blocked-running 硬挡；服务端其实已有入队、取消、取回草稿、插入本轮、重试、图片与重启恢复。顺序调整、普通文件、停止后暂停这三块服务端也缺。
  2. 对标下来，Codex Desktop 是功能最全的，但不是最好用的范本。它把「编辑/删除/引导/重试/继续/暂停/预览/重排」都做了，却把「排队」藏在快捷键和一个「…」菜单里，默认行为还是「引导」；Cursor 与 Copilot 赢在入口清楚和拖拽排序；Claude Code 与 Gemini CLI 是终端式的最小队列；ChatGPT 没有原生队列。
  3. 2.3.0 不抄任何一家，做「手机上一只手能完成」。发送 = 排队；停止 = 暂停；队列条常驻；点单条进操作面板；上下移而不是拖拽；「插入本轮」与「移到队首」分开；附件与引用原样保留；失败卡在队首，必须重试/编辑/删除才继续。
一句话定位：排队不是「把消息塞进一个列表」，是「在不打断当前工作的前提下，把下一句放在一个看得见、改得动、撤得回的位置」。2.3.0 以这条为标准验收。

1. 问题复现：那一刻发生了什么

Human 2026-11-20 19:55 的真机截图：一轮任务正在跑，输入框里已经有文字和一张图片，右下角只剩一个红色停止——没有发送，也没有「排队」。

代码因果链

ChatComposer.tsx:519-537：running 为真时只渲染 Stop，发送按钮根本不出现。

composerSubmit.ts:7-15：即使表单被提交，运行中也直接返回 blocked-running，草稿被保留，消息发不出去。

server.js：enqueueSend / cancelQueuedSend / steerQueuedSend / drainQueuedSend 都在，手机端一个都没接。

所以不是「从零做」

服务端已有：入队、取消（含取回草稿）、插入本轮（steer）、失败重试、图片、队列持久化、重启恢复、队列图片接口。

2.3.0 真正要补的是：手机端入口与操作面、顺序调整、普通文件、停止后暂停/恢复，以及一条能自证的验收链。

Turnloom 2.3.0 的两条后端边界：「附件随队列」的完整承诺只覆盖 Codex 本地后端（图片 + 普通文件）；PI 原生队列只支持图片。「插入本轮」在 Codex 本地是真并入当前轮；PI 原生只是置优先级（下一条先发），UI 会写成「优先下一条」，不会冒充 steer。

第一梯队：完整闭环

Codex Desktop 唯一把「编辑 / 删除 / 插入 / 重试 / 继续 / 暂停 / 预览 / 重排」都做齐的。它的问题不是功能，是入口与默认值。

第二梯队：队列好用，管理不全

Cursor Copilot 入口与重排最好，但单条编辑/删除/暂停/失败闭环要么没有，要么公开资料没写。

第三梯队：最小队列

Claude Code Gemini CLI 能排队、能取回/立即发，但没有单条管理。

缺口：消费级聊天仍没有

ChatGPT 没有原生队列；截至 2026-08 的功能请求仍开放，用户靠第三方扩展补位。

3. 逐个产品：好在哪、差在哪

Codex Desktop 26.1111 · 最完整，但「会的人才会用」 主基准

做得好：队列是逐条对象，不是一坨文本。每条能编辑、删除、引导（提交但不打断模型）、失败重试、中断后继续；有预览、图片/粘贴文本附件、重排、送达未确认状态，删除/编辑还能撤销。停止本轮后队列会暂停，并明确告诉你「因为你中断了当前响应」。

不够好：默认「后续消息」是引导，排队要按快捷键；设置项叫「后续消息处理方式」，藏在设置里；单条操作在「…」菜单，队列一多就要点很多次；没有移动端。

对我们的启发：功能面照它对齐，但默认值和入口反过来——手机默认排队，插入本轮做成单条动作；队列条常驻，不用记快捷键。

Cursor · 双通道最清楚，管理面最薄 入口范本

做得好：Enter 入队，Cmd/Ctrl+Enter 立即发送（绕过队列）；队列按顺序显示在当前任务下方，可拖拽重排；「Send now / 再按一次 Enter」把消息送到 agent 的下一个工具调用点，既插队又不中断正在进行的工作。

不够好：公开文档只讲「排队、重排、立即发」，没有单条编辑、删除、暂停、失败重试的说明；队列管理基本等于「改顺序 + 现在发」；附件随队列的行为没有写。

对我们的启发：「排队 / 立即发」必须是两个一眼可辨的动作，不能藏在一个按钮的第二次点击里；但手机没有 Cmd 键，所以拆成两个常显按钮 + 单条「插入本轮」。

GitHub Copilot Chat · 三选一最明确，但每次都要选 意图范本

做得好：发送按钮带下拉，三个选项写得极清楚：Add to Queue（等当前响应完）、Steer with Message（当前请求让位，新消息立刻处理）、Stop and Send（取消当前请求并立即发送）。多条待发消息可拖拽排序。这是把「用户到底想干嘛」讲得最清楚的一家。

不够好：官方标注 experimental；每次发送都要经过一个下拉，频繁排队时反而慢；没有单条编辑/删除/暂停/失败重试的记载；只在 VS Code 里。

对我们的启发：三选一的语义值得学，但手机高频动作不能每次弹菜单——默认排队，单条面板再给「插入本轮」，把选择留到真正需要时。

Claude Code · 键盘流最优雅，但是「全有或全无」 极简范本

做得好：运行中直接输入 + Enter 入队，消息灰显在输入框上方；↑ 把整个队列拉回输入框编辑/丢弃；Ctrl+Enter 立即发送；Esc 中断但保留已完成的工作，并把队列里的消息接着发。队列在工具调用结束的边界送达 Claude，不硬切。

不够好：只能整队拉回，不能单条删/改/排；队列是终端交互，没有附件与可视化管理；不支持拖拽；移动端不可用。

对我们的启发：「取回编辑」是最有价值的一步，但对多条消息必须逐条做；键盘流在手机上没有，所以用单条面板替代 ↑。

Gemini CLI · 最小可用，但取消会「合并」语义 底线范本

做得好：流式响应中可继续输入，队列以 `▸` 灰显在加载指示器下方；流结束自动按序发送；取消时把队列内容追加回输入框，不丢。

不够好：没有单条管理；多条消息在取消时用双换行合并成一条，原始分条语义丢了；没有附件/排序/暂停。

对我们的启发：「取消不丢」是底线；但合并消息会改变语义，2.3.0 的取回是逐条还原成独立的输入与附件。

ChatGPT · 消费级聊天仍没有原生队列 缺口

做得好：流式体验、停止/重新生成、移动端成熟度仍是行业基准。

不够好：运行中不能排下一句；要么等，要么停止。2026-08 的官方社区功能请求仍开放，Chrome 商店里有多个第三方「消息队列」扩展补位——这正说明需求真实存在。

对我们的启发：这不是「Agent 产品才需要」的功能；只要用户会「一边看它跑、一边想到下一句」，队列就是基础交互。

4.1 七个关键决策

① 发送 = 排队，停止单独一个红块

手机用户是「一边看它跑、一边想到下一句」，不是每次都想改变当前方向。默认排队，插入本轮留给单条动作；停止永远最右，输入为空时只留停止，位置不跳。

② 停止 = 暂停，不偷偷继续发

用户按停止，意图是「先别动」。队列暂停，必须点「恢复」才继续；恢复也要等 1.5s 空闲确认，且等待审批时绝不插队。

③ 队列条常驻 + 两级抽屉

队列条解决「有没有、几条」；列表解决「哪条、什么状态」；单条面板解决「改、插、排、删」。不做长按隐藏菜单，不靠手势猜。

④ 上下移，不做拖拽

手机单手操作，44px 按钮比拖拽稳、可测、无需教学；队列上限 20，逐条上下移足够。拖拽留给未来的大屏/长队列。

⑤「插入本轮」与「移到队首」分开

前者是 steer，进入当前轮；后者是顺序，下一轮先发。两个意图、两个按钮、两套提示；409 只报错，绝不把一个按钮偷偷变成另一个。

⑥ 失败卡在队首

FIFO 下失败只可能在队首；后续项不动，避免乱序。失败条进入直接展开该条详情，原因 ≤200 字，重试/编辑/删除三选一。

⑦ 附件与引用原样保留

图片、普通文件、引用块随队列项保存；取回时逐条还原。引用是纯文本块，不做假的结构化标记；单条详情原样可见。

没抄的那部分

不抄 Codex 的默认引导、Copilot 的每次下拉、Cursor 的拖拽唯一入口、Claude Code 的整队取回。它们各自成立，但都不是「手机单手 + 不打断」的最短路径。

4.5 后端能力边界：同一个按钮，不能两种行为

2.3.0 同时支持 Codex 本地队列与 PI 原生队列，两者能力不同。产品上不允许「按钮写着插入本轮，实际只改优先级」这种暗改；服务端把能力表随队列状态一起下发，客户端按表改文案和动作。

6. 验收：这次拿什么证明

按 docs/team/QUEUE_SPEC.md §6 逐条验收；下面是已经跑过的门禁与最终证据（含 APK 与线上 8787）。

功能链路

  • 运行中文字入队 → 本轮结束自动发出，只发一次。
  • 图片 / 普通文件入队 → 单条详情可见 → 结束后真实到达 Codex。
  • 3 条排队 → 上移/下移/移到队首 → 顺序持久化。
  • 取回编辑 → 文字/图片/文件逐条还原 → 再发成功。
  • 插入本轮 → 进入当前轮，不是下一轮。
  • 停止 → 队列暂停 → 不恢复不发；等待审批时不插队。
  • 队首失败 → 原因 + 重试 → 后续继续。
  • 20 条上限 → 第 21 条被拒，草稿保留。

视觉与设备

  • 390×844、390×640（键盘）、320×568：无横向溢出、按钮不换行、命中 ≥44。
  • 五种状态：空队列 / 1 条 / 发送中 / 暂停 / 队首失败，文案与状态一致。
  • 停止不位移；发送在左、停止在右；暂停条只留「恢复」。
  • 两级抽屉：返回队列可见，系统 Back 先关详情。
  • 真实照片在模拟器能显示（既有碎图回归）。
  • NB3 设计门禁签字；Vera 独立 E2E 通过。

7. 结论

排队是交流部分的核心，不是附加项。这次真正的教训不是「漏了一个按钮」，而是「服务端能力没有产品入口」——有能力却不被使用，等于没做。2.3.0 把入口、状态、操作、失败、暂停、附件、引用连成一条闭环，并且按「手机单手、不打断当前工作」重新设计，而不是把桌面产品的菜单搬过来。

对标结论：Codex Desktop 仍然是最全的功能基准；Cursor/Copilot 的入口与排序值得学；Claude Code/Gemini CLI 证明「最小队列」也有价值；ChatGPT 的缺口说明这是普遍需求。2.3.0 的目标不是拿第一，而是让 Turnloom 在手机上做到「看得见、改得动、插得进、停得下」——这四件事齐了，排队才算做完。
